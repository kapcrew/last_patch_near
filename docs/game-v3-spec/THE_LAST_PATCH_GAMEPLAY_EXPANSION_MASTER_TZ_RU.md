# THE LAST PATCH — GAMEPLAY EXPANSION MASTER SPECIFICATION

## Версия 3.0 · Game-First Rebuild · 14 ноября 2026

**Название:** THE LAST PATCH — A City Held Together by Open Source  
**Цель документа:** дать другому AI-разработчику недвусмысленное ТЗ на превращение присланного `THE_LAST_PATCH_WEB_DIST(1).zip` из короткого интерактивного прототипа в визуально единую, глубокую, реиграбельную браузерную пиксельную игру с отдельным проверяемым NEAR Testnet-контуром.  
**Срок игровой сессии:** целевое первое прохождение **90–120 минут** без необходимости GitHub-аккаунта, кошелька, ожидания реального Pull Request или других игроков. Это целевая метрика дизайна; соответствие подтверждается плейтестом, а не одним количеством текста.  
**UI/нарратив:** English. **Разработка/комментарии/документация:** могут быть Russian/English.  
**Ключевое требование пользователя:** не картинка, не скриншот и не косметический апдейт. Результат — рабочая игра из заменяемых файлов репозитория.

> ВАЖНО: Story Mode / game progression и Live Testnet bounty — разные слои. В Story Mode игрок решает локальные игровые задачи и получает только вымышленные ресурсы. Только подтверждённый контракт может разрешить выплату Testnet NEAR; эти награды не обещают денежной ценности. Фиктивные результаты никогда не показывать как реальные GitHub PR или транзакции.

## 0. ПРИКАЗ РАЗРАБОТЧИКУ: что НЕ считается выполнением задачи

НЕЛЬЗЯ завершить работу, прислав одну сгенерированную иллюстрацию, несколько PNG, макет Figma, набор новых иконок без интеграции, статический сайт, «планы на будущее» вместо игровых механик или архив, где 90% кнопок ни на что не влияют. Нельзя сохранять старую игру с четырьмя кнопочными сценариями и объявлять её расширенной из-за стилизации.

**Проверяется именно программный продукт.** Прежде чем что-либо менять: распаковать исходный ZIP; посмотреть каждый файл; запустить локальный HTTP-сервер; установить current-state baseline; описать текущие ограничения; сохранить контрактную модель и существующие работающие функции; зафиксировать план миграции. Далее реализовать полноценный игровой цикл со входом, движением, выбором задач, настоящими puzzle/mechanic stages, состояниями мира, прогрессом и сохранением. После внедрения любого спрайта проверять, что он реально применяется рендерером. Не использовать CSS Unicode-символы/emoji/Lucide/FontAwesome в качестве окончательных игровых иконок.

**Запрещённые fake-success паттерны:** немедленное обновление on-chain статуса после нажатия кнопки, `Math.random()` вместо проверяемого события, `localStorage` как источник Live-истины, выдуманные GitHub PR, выдача нарисованного числа за глобальный leaderboard, искусственное удлинение сюжета «подожди 5 минут», требование скачать несуществующий клиент, использование внешних защищённых спрайтов без лицензии.

**Выходные материалы:** исходники проекта, изменённые/новые файлы, актуальный asset manifest, game data JSON, Rust-контракт если возможно с unit/integration тестами, SQL/миграции только если есть backend, два сценария запуска Mac/production, README, video demo script, P0/P1 status, перечень фактически подтверждённых вызовов и evidence (tx hashes/URLs). Существующий проект не перезаписывать слепо; новые фичи изолировать.

## 1. Аудит загруженной сборки (проверенные факты)

Архив содержит 14 файлов: `index.html`, `style.css`, `config.json`, `assets/manifest.json`, `media/twilight-city.png`, `js/main.js`, `js/domain/logic.js`, `js/game/{WorldRenderer,BuildingPainter,AssetRegistry}.js`, `js/ai/fallback.js`, `js/github/evidence.js`, `js/chain/{wallet,rpc}.js`.

1. `index.html` — одностраничная оболочка со sidebar, основным canvas 640×360, четырьмя HUD-показателями и Questbook справа. Начальная страница уже имеет режимы `/`, `/sample`, `/live`, `/about`. Это оболочка приложения, а не полноценный сайт со страницами истории, персонажа, достижений и таблицы лидеров.
2. `js/domain/logic.js` — ровно **четыре** определения заданий: `bridge`, `well`, `library`, `forge`; у каждого пять локальных стадий через `sampleNext` (`BROKEN→CLAIMED→VERIFIED→AWAITING_REVIEW→RESTORED`). Мини-игр, инвентаря, событий или разветвлённой истории нет.
3. `js/game/WorldRenderer.js` — интерактивные точки ограничены четырьмя прямоугольниками, персонаж идёт по заранее заданным прямым waypoint-отрезкам и сразу вызывает экран квеста по прибытии. Нет произвольного движения, карты коллизий, патрулей NPC, сцен, порталов, погоды, смены времени суток и интерактивной среды.
4. `js/game/BuildingPainter.js` — примитивная процедурная отрисовка четырёх построек и персонажа из прямоугольников. Допустима как временный Fallback, но **не** как целевая графика. Качество заметно отличается от фоновой иллюстрации.
5. `assets/manifest.json` — уже предусмотрены URL `assets/buildings/{building}-{broken|progress|restored}.png`, изображения NPC и персонажа, но **эти файлы отсутствуют в присланном ZIP**, следовательно `AssetRegistry` переходит на procedural fallback. Первое обязательное действие — предоставить реальные согласованные изображения или авторские спрайты и интегрировать их, а не просто сослаться на несуществующие пути.
6. `media/twilight-city.png` — реальный красивый пиксельный фон 640×360: фиолетовое небо, горы, река, водопад, две тропы, береговые плато. Использовать как исходный стиль, палитру и один layer/reference, но НЕ выдавать плоский PNG за интерактивную тайловую карту.
7. `index.html` и `js/domain/logic.js` содержат текстовые символы (`✦`, `⌂`, `◈`, `⌘`, `◉`, `▣`, `⚙`, `⚒`, `↻`). Заменить именно **изображениями в единой пиксельной графике**.
8. `config.json` содержит пустой `contractId`; у приложения есть просмотр RPC и код NEAR wallet, но предоставленный ZIP не содержит Rust-контракт и никакого подтверждения развёрнутого договора/выплаты. Экономические функции не считать доступными до тестов в сети.
9. `js/github/evidence.js` и `js/chain/rpc.js` имеют основу для внешних связей; сохранить их ответственность, не переносить GitHub-вердикт в свободно подменяемый local state. Подлинность GitHub не выводится из цвета карточки.
10. В CSS доминирует обычная SaaS-сетка «sidebar / middle canvas / quest panel», а не игровой fullscreen/immersive опыт. Нужен новый игровой экран и сайт в единой пиксельной идентичности.

**Обязательная оценка baseline:** указать конкретные пути и фактические screenshots (если браузер доступен), какой режим работает, что не работает, сколько задач доступны, какие ошибки сети. Не путать наличие кода с проверенной on-chain работой.

## 2. Продуктовое видение и четырёхслойная структура

**Фантазия игрока:** «Я Patchkeeper — мастер, который чинит сломанные правила мира. Каждая исправленная системная ошибка физически меняет город. Обитатели помнят, что я сделал; за найденные решения получаю инструменты, доверие и доступ к новым районам». Для одного человека игра должна быть интересна без знания программирования. Терминология Git, зависимости, проверки и ошибки становятся фэнтезийными метафорами; игрок интуитивно понимает puzzle-механику, а в справке видит реальный аналог.

1. **Website / Portal**: отдельная эффектная пиксельная главная страница, описание, How it works, Sample Play, World Ledger, Leaderboard, About, Live Bounties, кнопка Play Now.
2. **Story Campaign (offline first)**: полноценная игра без регистраций, с исследованием мира, путешествием между районами, нелинейной картой поручений, задачами, мини-играми, диалогами, улучшениями, сбором ресурсов, достижениями, финалом.
3. **Community Layer (optional online)**: рейтинги прогресса, добровольный профиль, еженедельные challenge seeds и ghosts/records, если backend готов. Отсутствие backend не блокирует кампанию.
4. **Live Open Source / NEAR**: отдельная доска реальных issue; финансирование testnet bounty, claim, PR, review, withdraw, подтверждённое состояние контракта. Сюжетные награды не конвертируются в NEAR. Live-события могут оформляться как визуальный городской праздник при подтверждении on-chain `PAID`.

**Основной игровой цикл:** исследуй → найди дефект → поговори с NPC → собери контекст → реши задачу механикой → проверь решение → получи игровую награду → восстанови участок → открой путь/навык/новый сюжет → вернись к побочным задачам. Не сводить весь цикл к `claim → verify → review → restore`.

**Повествовательная тема:** The Silence / Broken Protocol. Город перестал слышать сам себя: сообщения теряются, часы идут вразнобой, дороги не соединяются, жители забывают обещания. История становится связной драмой о доверии и коллективном ремонте — не рекламным каталогом GitHub-задач.

## 3. Несдвигаемые правила реализации и приёмки

- **Полный игровой контент:** как минимум 4 районы, 28–32 содержательных сюжетных задач, 12–16 побочных поручений, 6 различных puzzle families, 10+ NPC с индивидуальными репликами, 5 инструментов, 4 стадии восстановления важных объектов, карта/журнал/инвентарь/навыки, 1 финальное сюжетное событие, 2+ различимых финальных варианта. Целевой runtime 90–120 минут без ожиданий/гринда; один только объём диалогов не засчитывается.
- **Различимые действия:** у задач разные модели поведения, а не один UI и смена текстового вопроса. Каждый puzzle должен реагировать на попытки, ошибку, подсказку и правильное решение.
- **Перемещение:** click-to-move и keyboard arrow/WASD (опционально с настройкой), A* на collision grid, плавная камера, кликабельные NPC/объекты, доступный аналог управлением с клавиатуры. При нажатии на уже открытый квест персонаж физически подходит к NPC.
- **Визуал:** чистый авторский pixel art в стиле фонового twilight-city; все игровые иконки, кнопки с символами, эмблемы задач, NPC и здания — sprite assets, не обычные glyph; `image-rendering: pixelated`; единая палитра и pixel-grid.
- **Достоверность:** story-награды (`Sparks`, `Patch Dust`, `Town Trust`) только игровые; Testnet NEAR только через wallet/contract. Протокол одинаково строг для зрителя и участника.
- **Сохранение:** прогресс офлайн сохраняется автоматически, экспортируется и импортируется JSON; новая версия game data мигрирует старые сейвы, не обнуляя весь прогресс.
- **Изменение города:** восстановленное здание визуально меняет фон, маршрут, NPC или доступные интеракции. Цветной бейдж и текст `RESTORED` без изменения ландшафта — не выполнение требования.
- **Дизайн сайта:** посетитель сразу видит живой игровой мир, персонажа, атмосферу, эффект наведения и привлекательный Play CTA. Нет «корпоративной SaaS-панели как основного первого экрана».
- **Итог:** содержимое должно запускаться локально без интернета в Story Mode после первого получения статических assets (или PWA cache), не падать при отказе GitHub/NEAR/AI.

| Дополнительные занятия | не менее 12 | side quest / discovery / challenge / minigame |

| Город без сети | стартует Story Mode | network offline integration test |

Цифры не являются заявленными достижениями нынешнего репозитория; это критерии будущей сдачи.

## 5. Приоритеты и границы в условиях хакатона

**P0 — немедленно, минимальный настоящий релиз:** единая качественная пиксельная идентичность; полностью играбельный пролог + первый район (6–8 квестов, 3 puzzle family), сохранение, живые NPC, лидерборд-local, один связанный live bounty flow на NEAR при наличии действующего контракта; с честными статусами. Реальная заявка лучше красивого обещания.

**P1 — содержательная игра для 90–120 минут:** все четыре района; полный сюжетный граф, 28–32 квеста, побочные активности, минимум 6 puzzle families, 10+ NPC, мини-игры, achievements, выборы и оба финала, существенно больше sprites и анимаций. Зависимость от отправки PR отсутствует.

**P2 — общественное расширение:** серверный verified leaderboard, еженедельные seed-челленджи, social ghosts, guilds/settlements, мультигородская сеть bounty, GitHub App/CI/Webhooks, offline PWA install, контентная система редактора.

**Нельзя сознательно отказаться от P1 в итоговом задании:** пользователь просит расширение до полноценной игры. Однако нельзя делать вид, что весь P1 создан, если реально выполнен только P0. Реализатор должен честно оставить `[DONE]`, `[IN PROGRESS]`, `[NOT DONE]` по каждому модулю и продолжать работу максимально долго в текущем запуске, без выдачи дизайн-документа за код.

## 6. Художественная режиссура — единство мира, а не смесь стоков

Центральный арт-референс текущей сборки — `media/twilight-city.png`: 640×360, насыщенные фиолетово-синие и розово-янтарные закатные тона, тёмные хвойные силуэты, бирюзовые реки, гранитные берега, ступенчатые тропы. Персонажи и здания должны соответствовать масштабу, детализации, освещению, точке зрения и перспективе фона. Не брать картинки с разным ракурсом (изометрия/side-view/top-down) в одну сцену.

**Требования:** пиксельная сетка 1× без blur; тайлы 16×16 или 32×32 исходных пикселя (выбрать один базовый стандарт), NPC 24×32 или 32×40 по выбранному масштабу, контуры 1–2 px, 4–6 оттенков на основной материал, структурированный highlight/shadow, минимум случайного шума, геймплейные объекты читаются на любом background. Ландшафт темнее активных персонажей; UI-panel контрастен; эффект glow делается несколькими пиксельными градациями и световыми слоями, а не smooth blur вокруг каждого объекта.

**Что категорически запрещено:** большие generic emoji, Unicode вместо иконок, SVG из типовой библиотечной иконки как «арт», фотографические cutout-картинки, несогласованные размеры пикселя, анатомически сломанные спрайты, статические NPC без реакции на игрока, любые изображения с водяным знаком, незапрошенные стилизации под узнаваемые защищённые игры.

**Порядок поставки графики:** сначала загрузить пользовательские иллюстрации из другого проекта → сделать визуальный аудит разрешённости, размеров и ракурса → согласовать карту использования → добавить в assets manifest → только потом при нехватке отдельных компонентов делать новые оригинальные спрайты в идентичной палитре. Иллюстрации с другого проекта не копировать без разрешения правообладателя. Не модифицировать принципы дизайна исходного предоставленного изображения без необходимости.

## 7. Техническая система графики

Визуальный движок: Canvas 2D с `imageSmoothingEnabled=false`, `requestAnimationFrame`, масштабированием по целочисленному коэффициенту где возможно. Game design resolution `640×360` или ближайшее кратное выбранному tile grid (проверить совместимость с текущим background). Игровой мир разделён на независимые tilemap zones, а не один static background. Статический фон может быть distant parallax layer только в 1-м районе. Каждая зона имеет layers `background`, `ground`, `decals`, `collision`, `props`, `actors`, `foreground`, `weather`, `lighting`; все gameplay-маркеры располагаются через координаты data, не hardcode в renderer.

**Asset manifest V2:** `id`, `type`, `path`, `spriteSheet`, `frameWidth`, `frameHeight`, `animations`, `anchor`, `zLayer`, `atlasGroup`, `collisionBounds`, `paletteGroup`, `fallbackAllowed`, `license`, `source`. При инициализации прогружать required assets до открытия игры; выводить отчёт `missing required assets` в dev console и не маскировать недостающую графику в prod без явной диагностики.

**Player sprite:** `idle4` 4 направления × 4 кадра; `walk4` 4×6; `interact` 4–6; `repair` 8; `hurt/stumble` 4; `celebrate` 8; `sleep` 4; `carry` 4; small shadow + breathing loop. `NPC`: минимум idle 4, talk 4, walk4 по 4 и emotional reaction 3; уникальные силуэты. Атласы с прозрачностью PNG/WebP без anti-alias и без контуров разной толщины.

**Мир:** не менее 16 визуальных пропсов для каждого района, 4–6 фоновых вариантов по статусу, 12 интерактивных объектов, передний план перекрывает персонажа по z-index Y, water animated 4–6 frames, particles pixel-based 1–3 px. Погода и освещение влияют только на настроение и необязательные исследования, не ломая читаемость задач. Поддержать `reducedMotion`, настройки FX и выключение screen shake.

**Договор на анимацию здания:** status `BROKEN` — разрушенные тайлы, недоступная дорожка, плачущий/испуганный NPC, негативная эмбиент-атмосфера; `IN_REPAIR` — леса, искры, рабочие, ремонтный SFX; `RESTORED` — структурно новая спрайтовая версия, открытый проход, NPC использует объект, изменение маршрутов/новый side quest. ## 9. Игровая камера, движение и интерактивная среда

**Навигация:** click/tap-to-walk к целевому тайлу; WASD/стрелки для desktop опционально. A* pathfinding по `collisionGrid`, стоимость клетки 10 ортогонально / 14 диагонально (или запретить диагонали, но быть последовательным); блокированные выходы доступно объясняются (`Bridge route offline. Repair the crossing.`). Обновление пути при изменении status мостов, дверей, тумана, NPC. Игрок останавливается в `interactionRadius`, повернувшись лицом к объекту; `E`/tap взаимодействует. ESC/Back закрывает диалог/окно, не откатывая сохранение.

**Камера:** follows player с deadzone 20% viewport, soft lerp, ограничения по краям зоны, 2×/3× integer zoom, телепортация по переходам без движения сквозь стену, медленный reveal restored structure. На mobile pinch zoom опционален; drag map не должен случайно запускать квест.

**Сцены:** карта мира (overview), 4 district scenes, 2 интерьерные сцены (library/forge), 1 финальная restored town scene. В каждом районе 3–4 спрятанные находки, 3–5 NPC, не менее 6 interactables и две короткие диалоговые реакции на прогресс. На карте отмечаются только открытые локации.

**Погода:** 3 состояния `clear/twilight/rain` сменяются детерминированно после событий (не таймер заставляющий ждать), эстетика. Ночной режим не блокирует задачи. Реиграбельность от вариативных маршрутов и optional challenges, не от ненадёжного random seed.

**Секреты:** 12 фрагментов прошлого, 4 hidden NPC scenes, 8 small achievements for exploration. Система не должна принуждать читать весь лор для завершения обычной кампании.

## 11. Правила квестового движка

Квесты авторятся декларативно (JSON/TS data), каждый имеет `id`, `arc`, `district`, `title`, `prerequisites`, `startTrigger`, `npcId`, `beats[]`, `puzzleId`, `winCondition`, `failDialog`, `hintLadder`, `reward`, `sideEffects[]`, `estimatedMinutes`, `tags`, `optional`, `storyFlags`, `version`. Ни один quest не зависит от hardcoded DOM id или живого URL GitHub, если это Story Quest.

**Quest lifecycle:** LOCKED → AVAILABLE → ACTIVE → CLUE_READY → PUZZLE_OPEN → SOLVED → TURN_IN → COMPLETED. `FAILED_ATTEMPT` — событие/счётчик, не перманентный quest status. При неожиданном закрытии вкладки игра поднимает состояние puzzle checkpoint; повторное вручение награды не допускается.

**Prerequisites:** `allOf/anyOf` из флагов, не циклические ссылки. Автоматический тест проходит DAG, находит недостижимые задачи, вычисляет min/max прохождение, проверяет отсутствие softlock. UI всегда показывает 1 доступную основную задачу и минимум 1 побочную после tutorial. Логика подсказок зависит от неудачных попыток (на третьей, на пятой), но не спойлерит ответ сразу.

**Мир реагирует:** quest effects атомарно сохраняются вместе с завершением, events публикуются в EventBus, WorldStateSystem обновляет tilemap/lighting/NPC/dialogue; при повторной загрузке World восстанавливается из snapshot. `quest-complete` не должен вызывать `withdraw_reward` — сети изолированы.

## 12. Шесть обязательных типов головоломок с геймплейными правилами

### A. Dependency Weaver («Нить зависимостей»)
Игрок перетаскивает 4–8 узлов-компонентов на дорожку, соединяет взаимозависимости и устраняет циклы; каждое соединение проверяется на topological order; ошибочная дуга подсвечивается красным и блокирует test-run. Начальный tutorial: три сегмента мостовой цепи; продвинутый challenge: 7 узлов + конфликт версий. `Solve` только после проверки DAG, а не по нажатию `Submit`. Варианты отличаются графом и допустимыми топологическими порядками.

### B. Nullflow / Water Routing («Сухой колодец»)
Игрок направляет поток от source к endpoint по решётке 5×5 → 7×6, ставит `fallback`/`filter`/`check` tiles; при null packet потоки не должны падать. Симуляция прогоняет фиксированные test vectors; отображается path трассировки + ошибка в конкретном узле. Старт: один null и два клапана; позднее два асинхронных входа и timeout.

### C. Diff Detective («Архив пропавших строк»)
Сравнение двух мини-файлов: слева broken version, справа needed behavior. Игрок выбирает/упорядочивает 2–5 строк для короткого патча, исправляет env переменную, путь или отсутствие guard. Валидатор семантический по AST мини-языка/заранее определённым токенам — не по точному копированию строки, если ответ допускает эквиваленты. Показывать почему тест упал/прошёл. Это **не реальное выполнение непроверенного JS из input**.

### D. Clock Sync / Event Ordering («Часовая башня»)
События приходят в перемешанном порядке; игрок расставляет их в причинно-следственную последовательность, чтобы предотвратить дублирование сигнала. Поначалу 4 события без параллелизма, затем 6–8 с дедупликацией nonce и retry. Условие победы: все required dependencies satisfied, одно событие не исполнено дважды.

### E. Signature Gate («Печать кузницы»)
Нужно назначить роли на действия (`maintainer`, `patcher`, `guardian`, `visitor`), проверить разрешённость операций по матрице, отбить фальшивое «одобрение». Механика — drag role badge to action + run tests; автоматическое объяснение каждой ошибки. **Никаких настоящих приватных ключей**, имитация security-проверок происходит только в Story.

### F. Signal Relay («Тёмный маяк»)
Сетевая puzzle: направить сообщение через 3–6 узлов, сохранив sequence id и checksum, с ограничением одной перегрузки/потери пакета; пользователь ставит repeater, dedup, buffer; карта показывает анимацию packets. Цель — доставить 100% из трёх обязательных сообщений, не пропустить duplicate при retry. В сложном варианте компромисс задержки и надёжности.

**Дополнительные мини-игры P1:** Rhythm of Repairs (не музыкальное копирование, а timing/precision press с оригинальными сигналами), Archive Sorting (pattern classification), Lantern Search (observation), Cart Logistics (route optimization). Все 6 базовых типов нельзя заменить одним button press — обязательные рабочие rules, attempts, hints и визуальные feedback states.

## 16. Диалоговая система и содержание текста

Введи `DialogueScene` с `speakerId`, `portraitEmotion`, `lines[]`, `choices[]`, `conditions[]`, `effects[]`, `voiceHint`, `skipAllowed`, `seen`. Выборы визуально делаются отдельными пиксельными кнопками внутри dialogue box, поддерживают keyboard, touch и screen-reader alternatives.

**Пример authored English-диалога из пролога:**

> Bridgekeeper: “The river didn't swallow our bridge. A promise did.”  
> Patchkeeper: “A promise?”  
> Bridgekeeper: “One piece waited for another. Then another. Nobody ever said ‘go.’”  
> [Show me the broken chain] [What happened to the townsfolk?]  
> Bridgekeeper (after puzzle): “You didn't mend the wood. You reminded it where to stand.”

**Пример failed attempt:** “That sequence makes the second worker depend on itself. Follow the lines—where can the flow begin?” (конкретная помощь, а не «Wrong answer»). **Локализация:** все строки в `/content/en/*.json`; код не содержит больших HTML-вставок с английским лором; позже можно добавить русский перевод. **Темп:** каждая реплика 1–2 коротких предложения, игрок может пропустить уже увиденные диалоги; автоматический текст не обязан звучать как техническая документация.

**Нарративные варианты:** `charter_choice = open_source | caretaker`, `trust_high` при >=70, `memories_found >=8`; итоговые сцены отличаются декорациями, 3–4 диалоговыми строками, выбором последнего городского символа, но не блокируют базовую победу. Мораль: код и люди нуждаются в ответственности; AI — помощник, а не правитель.

## 17. Инвентарь, предметы и крафт

В кампании нет бесконечного мусорного лута. Инвентарь — максимум 24 слота (без stack limit для валют), 5 основных инструментов, 12 story fragments, 10 коллекционных памятных предметов и 8 расходуемых gameplay tokens (подсказки, фонарь, знак маршрута). Каждому предмету обязателен уникальный icon sprite, короткое описание и видимый эффект; редкие предметы нужны для лора, но ни один критический quest не может быть навсегда потерян из-за выброшенного предмета.

**Инструменты:** Lens подсвечивает разорванные connections на 2 сек; Tuner показывает одно выбранное null flow; Needle визуализирует один конфликт dependency graph; Stamp отображает роли и разрешения, не подписывает криптографически; Bell прокручивает последний event step в time puzzle. Cooldown/заряд только внутри конкретной puzzle; если предмет отключён accessibility setting, puzzle остаётся разрешимой через альтернативную подсказку.

**Crafting:** 6 фиксированных рецептов, например Signal Lantern = Copper + Glow Dust; Repair Kit = Wood + Patch Dust; Archive Bookmark = Ink + Paper. Материалы получаются детерминированно из квестов/исследования; нельзя случайно потратить единственный mandatory material на optional cosmetics и получить softlock. `craft()` транзакционен и идемпотентен относительно `craftEventId`.

**Shop:** Story shop продаёт декоративные рамки, цвет фонаря, портрет в профиле, украшения домика; цены Sparks, покупки только локальные, не NFT. Торговец отвечает меняющимися фразами после major quests, но не умеет принимать NEAR в story economy.

## 18. События, интерактивность и ощущение жизни

- **NPC schedules:** жители перемещаются между 2–3 точками в зависимости от квестов, используют мебель, взаимодействуют между собой; schedule не основан на реальном 24-часовом ожидании. Поведение deterministic by chapter.
- **Ambient microevents:** стая птиц взлетает после ремонта, дети пересекают мост, колодец пульсирует, книжные страницы вылетают из окна, кузница выпускает искры, фонарь меняет свет, гном-почтальон уносит письмо; минимум 12 событий с привязкой к story flags.
- **Optional interactions:** читать табличку, осмотреть дверь, починить фонарь, покормить городскую птицу, поговорить со странником, найти старую запись, открыть коробку с картой; каждый prop — unique one-line reaction, иногда optional reward.
- **Immediate feedback:** на правильный ход — пиксельная анимация, SFX, обновление puzzle test status; на ошибку — читаемая подсветка причины; на milestone — от 1 до 3 секунд короткой non-blocking cutscene.
- **Трекеры:** journal содержит completed/open/locked, карту с открытыми зонами, коллекции, city health, текущую цель, количество уникальных задач и статистику попыток; можно отключить intrusive notifications.
- **Ритм:** чередование поговорить/исследовать/решить/вернуться/побочная находка, не три подряд одинаковые puzzle. Sequence planner автоматически предупреждает, если два обязательных подряд одного семейства после tutorial.

## 19. Реиграбельность, задания дня и рейтинги

**После кампании:** Challenge Board с повторными, автоматически выбираемыми, но детерминированными уровнями шести puzzle families (`seed`, `difficulty`, `solverVersion`). Игрок улучшает результат без повторного получения основной награды. Доступно 3 сложности и 12 seed challenges в базе; weekly seed публикуется только при наличии backend, иначе локальный `DAILY CHALLENGE — LOCAL RECORD` с прозрачным статусом.

**Score objective (не зависит от кошелька):** `score = base(1000) + speed_bonus(max 0, 300 - elapsed_seconds*2) + no_hint_bonus(100) + accuracy_bonus(150 if <=1 failure else 0) - retry_penalty(20*retries)`. Счёт не может быть меньше 100. Этот score годится для локального сравнения, но доверять присланному браузером результату в глобальном рейтинге нельзя.

**Три рейтинга:**
1. `Story Hall of Patchkeepers` — локальное достижение, процент story completion, playtime, discoveries, total game Sparks; пометка `ON THIS DEVICE`.
2. `Daily Challenge` — серверный verified leaderboard **только если** backend проверяет подписанный session/seed и воспроизводимый input transcript; при отсутствии проверки `Unverified / Just for fun` и никакого ранжирования якобы глобального.
3. `Live Patches` — публичная таблица фактических оплаченных контрактом bounty, `accountId`, `paidCount`, `totalTestnetNear`, `tx`, `PR` (только эти доказанные поля), раздельно от вымышленных Sparks. On-chain leaderboard нельзя подменить локальными story statistics.

**Антинакрутка:** для публичных achievements сервер выдаёт nonce/challengeToken и фиксирует версию seed, валидирует последовательность puzzle moves с лимитом частоты и hash transcript; всё равно считать рейтинг experimental, не «невзламываемым»; IP/UA не использовать как единственный идентификатор. Ограничить максимум сабмитов, избежать self-funding farming badge, отключить финансовую мотивацию за быстрые Story scores.

**Награды:** cosmetic badges (Builder, Archivist, Relay Keeper, Town Healer, Full Clear), pixel-frame profile borders, optional epilogue scenes. Никаких jackpot, raffle или денежных призов за random wins.

## 20. Сохранение, экспорт, миграции, продолжение

`SaveGameV3` содержит: `schemaVersion`, `profileId`, `createdAt`, `updatedAt`, `chapterId`, `districtId`, `playerPosition`, `questStates`, `puzzleCheckpoints`, `worldFlags`, `inventory`, `resources`, `npcMemory`, `dialogueSeen`, `achievements`, `sideQuests`, `gameSettings`, `playTimeSeconds`, `endingChoice`, `saveChecksum`. Использовать IndexedDB (предпочтительно) + fallback localStorage только для небольших настроек. Save-данные не являются подтверждением Live транзакций.

**Автосохранение:** после успешного puzzle beat, получения награды, перехода зоны и настройки; debounced 300–1000 ms; хранить не менее двух snapshot revisions для восстановления при порче. При JSON corruption показывать `Restore last good save / New game`, не стирать молча. Начать новую игру можно в отдельном save slot (3 слота).

**Экспорт:** download `.lastpatch.json` с версией, checksum, metadata; импорт валидировать через schema (Zod/JSON Schema), отклонять неизвестные опасные поля, не выполнять скрипты и не загружать remote URLs. Пользователь может удалить всё локальное состояние. В debug/dev mode есть `Reset Sample Story` и seed-specific fixtures.

**Миграции:** `v1` старые статусы четырёх объектов → `v3` flags без выдачи наград/подмены контрактов, `v2` animated map IDs → `v3` zone ids. Тест на импорт старой версии обязательный; в крайнем случае показывать контролируемый recovery wizard.

## 23. Финансовые и контрактные ограничения NEAR

**Истина Live:** контракт Rust near-sdk и подтверждённые RPC данные, не UI, не AI, не GitHub alone. Контракт в предоставленном web-dist **отсутствует**, поэтому исходный код/деплой Rust — отдельный обязательный пакет, если они не будут предоставлены в следующем чате.

**Роли:** `maintainer` (создатель и funder bounty), `worker` (один утверждённый исполнитель), `spectator` (view-only), `contract` (gas/accounting); AI с ролью ноль. Для P0 один bounty может быть привязан к одному buildingId, но story state нельзя перезаписывать live status. Суммы native NEAR хранить в yoctoNEAR с decimal parsing (`1 NEAR = 10^24 yoctoNEAR`). Storage accounting отделять от reward, не делать опасных фиксированных гарантий возврата.

**Состояния bounty:** `OPEN` → `CLAIMED` → `SUBMITTED` → `APPROVED` → `WITHDRAWING` → `PAID`. Возможны `CANCELLING/CANCELLED` только при допустимых условиях. Отдельные `REJECTED`/`REVISION_REQUESTED` — если готовы контракты и тесты. `WITHDRAWING` никогда не считать успешной оплатой, пока callback не подтвердит outcome; failure возвращает retryable authorized state, не удваивая баланс.

**Методы (ориентир, сверить текущий ABI):** `create_bounty(repo, issue_number, title, building_id, reward_yocto)` payable; `claim_bounty(id)`; `submit_patch(id, pr_url, commit_sha, evidence_sha256)`; `approve_patch(id)`; `withdraw_reward()` или `withdraw_reward(id)` — выбрать один контрактный ABI и зафиксировать; `cancel_bounty(id)`; `get_bounty(id)`; `get_bounties` с pagination; `get_maintainer_bounties` index query. `on_withdraw_complete` private callback must check expected result and nonce. Условия каждого метода и authorization проверяются on-chain.

**Делать правильно:** role checks по `predecessor_account_id`; validate IDs/length/max metadata; track pending promise and prevent reentry/double withdraw; callback restricted to current account; calculate locked funds and storage deposit separately; failure handler compensates/resets state after failed async transfer; no privileged direct `set_paid`; paid only after successful transfer. Tests cover multiple simultaneous withdrawals, failed promise, invalid signer, duplicate PR, cancellation race, insufficient balance, malformed receiver.

**Не делать:** хранить персональные API-токены/документы/полные PR diffs on-chain; обещать trustless проверку GitHub, финансовую доходность testnet токенов; считать `submitted` равным merged; открывать выплаты всем посетителям; платные story rewards; real mainnet без аудита.

## 24. GitHub-слой: реальные задания как отдельный режим

**Сценарий Live:** maintainer указывает публичную Issue (allowed owner/repo, валидные URL), подписывает финансирование Testnet NEAR → worker claims → открывает GitHub issue, готовит и публикует PR → UI получает read-only GitHub evidence (repo, PR, head SHA, merged state, linked issue, CI result) → maintainer лично проверяет и подписывает approve → worker withdraw → по callback контракт состояние PAID → город добавляет отдельную публичную метку `Live Repair Completed`, а story campaign от этого не зависит.

**Проверка:** `GET /repos/:owner/:repo/issues/:num`, `GET /repos/:owner/:repo/pulls/:num`, `GET /repos/:owner/:repo/commits/:sha/check-runs` с versioned API; rate limiting, safe URL allowlist github.com, issue belongs same repo; linked issue проверять из GitHub evidence, но не сводить к текстовому совпадению без review. Важное уточнение: statuses/conclusions у check runs имеют несколько состояний, и `neutral`, `skipped`, `stale` не равны успеху по умолчанию. <span>GitHub не должен давать backend удалённое исполнение чужого PR.</span>

**Trust boundary:** GitHub API может вернуть статус merged, но это не on-chain oracle; maintainer самостоятельно принимает работу и подписывает транзакцию. Статус `PAID` не означает аудита всей безопасности кода. В UI ссылки `See public PR`, `View contract`, `View tx` обязательны; если GitHub rate limited — понятный read-only error и ручная проверка, но UI не должен без доказательств показать green verified.

**Приоритет:** P0 один действительный bounty для мостика, остальные story. P1 расширение live board до нескольких GitHub projects с page cursor + sandbox funding data. Не создавать PR от лица пользователя без его явных прав и подтверждений.

## 25. AI Patch Guide / NPC Assistant

AI-помощник — дополнительная функциональность, не опора на внешнюю сеть для победы в Story. Интерфейс — пиксельная книга или говорящий механический ворон, который объясняет **текущую** puzzle в мире игры и при необходимости технический аналог. При ответе ссылаться только на whitelist `questContext` (id, hints, attemptedActions, rules, NPC context) и проверенные факты; не выдумывать PR, баланс, on-chain events, GitHub checks, игровую награду и новые условия.

**Два режима:** `IN_WORLD` — короткие художественные объяснения для игроков без опыта кода; `DEV VIEW` — связь puzzle с реальными понятиями (dependency graph, null guard, CI, nonce, permission). Выбор режима переключается в UI. 3 уровня подсказок: story hint / specific clue / explain failed test. Для Story есть локальный fallback hints: продукт играбелен при отключении AI/API.

**Safety:** не отправлять private file contents на внешнее LLM без согласия, хранить минимум telemetry событий, rate-limit request, prompt injection из GitHub Issue/PR использовать как неисполняемый текст; никогда не позволять LLM вызывать `approve_patch`/`withdraw_reward` автоматически; любые tool calls требуют пользователя и действующих прав. В конфигурации no API keys on public client.

**Acceptance:** 1) AI down → fallback работает, 2) AI не выдумывает успешность puzzle при failed test, 3) prompt injection в названии issue не меняет wallet адрес, 4) ответ <= 140 слов в UI, 5) hints ускоряют понимание, но не делают game one-click.

## 26. Лидерборд: backend / API спецификация

Публичный leaderboard — P1/P2, но локальный ranking и scoreboard нужны уже P0. Если сервер не готов, явно показывать `LOCAL RECORDS — THIS DEVICE ONLY`, а не имитировать 500 игроков. Никогда не выдавать никнеймы/аватары людей без согласия.

**REST endpoints (предложение):**

```text
GET  /api/health
GET  /api/content/version
GET  /api/challenges/daily
POST /api/challenges/:id/start    -> signed challenge token, expiry, seed
POST /api/challenges/:id/finish   -> moves transcript, score proof
GET  /api/leaderboard?mode=daily&cursor=...&limit=50
GET  /api/leaderboard?mode=live_patches&cursor=...
GET  /api/profile/:id           -> public opt-in fields
POST /api/profile/privacy       -> privacy toggle
```

**SQL сущности:** `leaderboard_users(id, display_name, consent, created_at)`; `challenge_definitions(id, seed, solver_version, starts_at, ends_at, config_hash)`; `runs(id, user_id, challenge_id, transcript_hash, replay_blob_key, score, verified_at, status)`; `ranking_cache(challenge_id, rank, run_id, recalculated_at)`; `live_patches(bounty_id, account_id, paid_at, tx_hash, amount_yocto, chain_height)`; `audit_events(...)`. Индексы по `(challenge_id, score desc, verified_at asc)` и `(account_id, paid_at)`; server-side validation of all input.

**Privacy:** псевдонимы с allowlist characters, profanity moderation minimal, возможность анонимного участия, удаление profile, leaderboard opt-in. `NEAR account ID` показывать только в Live transaction scoreboard, где оно является публичным on-chain фактом; предупреждать пользователя перед привязкой. Прогресс кампании без регистрации не синхронизируется автоматически.

**Валидация результата:** signed session ID, expiry, seed, version, checksummed ordered puzzle moves, server replay solves true, rate limit per session/account, deny negative timings / impossible move counts. Не обещать абсолютную anti-cheat защищённость браузерной игры.

## 29. Производительность, mobile и тестовая матрица устройств

**Desktop:** Chrome, Firefox, Safari (последние стабильные доступные версии), 1280×720 и 1440×900, вьюпорт игры масштабируется letterbox без размытия. **Mobile:** iOS Safari/Chrome 390×844, Android Chrome 360×800; с thumb-friendly controls и вертикальным compact quest UI. Canvas не должен быть шириной 640 CSS px на мобильном с horizontal scrollbar.

## 33. Детальная постановка четырёх районов и карта уровней

**Физический game world** должен отличаться от исходного статического 640×360 PNG: 4 отдельных tiled scenes плюс interiors. Ландшафт — из задника, tile layers и animated props; если из имеющейся иллюстрации нельзя корректно извлечь редактируемую карту, её используют только как неподвижный атмосферный слой пролога, а новые тайлы рисуют под такую же перспективу. Реальное прохождение и коллизии существуют отдельно от картинки.

### District 1 — The Fractured Crossing

40×24 базовых тайлов, центральная река и два разорванных пути, слева живой колодец, справа разрушенный мост, сверху дорожка к лагерю; точки входа: southwest spawn, bridge northbank, well, courier camp; замкнутый маршрут без мягкого лока, до repair player доступны обе половины района через обходную тропу/паром. Арт: фиолетовые горы, река, розовые деревья, тёплый фонарный лагерь; 3 варианта: before, scaffolding, restored. Нужны 12 интерактивных props, 4 NPC, 4 discoverables, 8 main + 4 side. Стартовое обучение длится <=4 минут, первая награда за solved puzzle видна в мире.

### District 2 — The Lantern Quarter

45×26 тайлов; площадь с лавками, часовая башня, гостиница и освещённые переулки. До ремонта квартал сумрачный, световые цепи не синхронизированы, двери плохо открываются. После ремонта появляются персонажи, откроется второй этаж таверны, рынок, вечерние гирлянды. Уровень содержит 3 изменяемых building clusters, 5 NPC walk cycles, 3 интерактивные лавки, минимум 4 optional prop discoveries. Puzzle сложнее за счёт событий и правил доступа, но не повторяет 8 квестов акта I.

### District 3 — The Drowned Archive

45×26 тайлов; у нижней лестницы вода, полуоткрытый архив, стеллажи, тайный подвал, сад памяти и стеклянное окно на реку. Два коротких interior map levels: flooded foyer + main library with retractable bookcases; world lighting shifts from blue to warm candle when repaired. Должна появиться новая exploration механика: вращение tile valves, поиск документов на полках, открытие secret passages; квесты связаны с lorenotes, но не превращаются в 30-минутную читку.

### District 4 — The Foundry Ridge

48×28 тайлов; возвышенность с кузницей, сигнальной башней, шахтным проходом, механическими лифтами (визуальные travel gates), центральным Machine Heart. Сначала часть платформ выключена; после починки forge/clock towers мир просыпается. Обязательная финальная последовательность: 4 сигнальные луча по районам, стыковка пазлов, массовое включение фонарей, вылет птиц и поступательное изменение цветов. Финал должен иметь настоящие игровые input steps, а не просто 30-секундный ролик.

**Размеры — исходные design targets, допускается изменение при сохранении плотности квестов и маршрутов.** Нельзя отмасштабировать один фон на 4 района и сменить названия: визуальные декорации и map layout должны быть различны.

## 34. Гейтинг пути и отсутствие softlock

**Модель открытий:** акт I открыт с первой секунды, после CR-06 физически пересекаем мост, после CR-08 открывается gate Lantern Quarter, после LQ-08 — flooded pass to Archive, после AR-08 — Foundry Ridge. Открытие должно быть отражено в tile collision map и minimap; при переходах `SceneManager` сохраняет позицию последнего безопасного spawn. Side quests не являются жёсткими gates.

**Recovery:** если персонаж оказался в разрушенной геометрии после изменения здания, relocation to nearest walkable tile через BFS; если puzzle UI закрылся или обновилась страница, checkpoint восстанавливается; если потерян required item, появляется deterministic fallback pickup у соответствующего NPC. Сброс Questbook не сбрасывает флаги мира; повторное прохождение puzzle как challenge не переписывает main story flags. Любой quest может быть завершён только после завершения обязательных beats, а решение можно проверить независимо через test fixture.

**Контроль:** CI строит directed graph из 32 quests, проверяет однозначные IDs, reachable end node, отсутствующие dependencies, невозможные mutually exclusive flags, отсутствие обязательного softlock. Нужны `npm run validate:quests` и HTML-отчёт со списком потенциальных проблем.

## 37. Контрактные event logs и модель событий UI

Контрактные view states надо читать через определённый `NearReadAdapter`. UI `NearWriteAdapter` отвечает за connect, request signing, pending states and receipts. `LiveRepairProjection` преобразует `Bounty.state === PAID` в **отдельный визуальный live badge** и событие салюта; нельзя менять кампанийный флаг `CR-06` только из-за on-chain оплаты. Объединение состояний допустимо как тематический, но не авторитетный overlay (текст «This bridge also has a real-world patch!»).

**Пример Live UI event flow:**

```text
BountyCreated(confirmed receipt) -> map live badge: FUNDED
BountyClaimed(confirmed receipt) -> worker silhouette/icon
PatchSubmitted -> GitHub proof sidebar, no rewards yet
MaintainerApproved -> pending withdraw available
WithdrawRequested -> PROCESSING state, no restoration
PromiseCallbackSuccess -> PAID badge + chain link + celebration
PromiseCallbackFailure -> retry availability / state restored, no celebration
```

**On-chain events:** для indexer логировать NEP-297-like consistent JSON со schemaVersion и ключами `event`, `bounty_id`, `maintainer`, `worker`, `amount_yocto`, `state`, `tx_hash?` (tx хеш клиент выводит из response, не пытаться заранее обещать его внутри контракта). Все `Rust` async transfer callbacks должны быть отдельно протестированы в sandbox.

## 38. Безопасность сайта и цифровых данных

Content Security Policy, no `unsafe-eval` in production, URL allowlist для внешних GitHub references, escape/sanitize внешние titles/issues/PR, ограничения markdown rendering, no user-generated script injection в dialog. В Story save импортировать только значения проверенной JSON schema, с лимитом размера 1 MB и длины строк. Не сохранять wallet private keys, seed phrases, GitHub PAT, LLM key в localStorage/базе. Ключи backend only, только необходимые scope.

Rate limit leaderboard endpoints, issue lookup caching, no public arbitrary URL fetch/SSRF; проверять HTTPS, разрешать `github.com` и `api.github.com` по точным hostnames, reject redirects to private IP. Не исполнять непроверенный код PR, не вставлять HTML из Issue напрямую. CSP не должна блокировать static sprite assets и согласованный wallet origin.

На NEAR contract проверять storage/deposit/gas/role/reentrancy failure; действия по выплате подписываются настоящим кошельком. Никакого связанного с азартной игрой real money wager или обязательного пополнения для прохождения Story.

## 41. План валидации качества контента

**Контентный аудит** должен анализировать каждый quest на совпадение механики, NPC voice и chain of events. Нужно не менее 6 типов mini-games и не более двух сюжетных заданий подряд с точно одинаковой формой решения. `FailureText` осмыслен; `HintText` не спойлерит решение немедленно; `WorldEffect` виден и проверяем. NPC reactions должны зависеть от фактических флагов: Bridgekeeper до CR-06 боится мостика, после CR-06 радуется crossing и ведёт историю о людях.

**Playtest protocol:** участник без знания проекта начинает новую игру. Наблюдатель фиксирует control friction, номер задания, время puzzle, число неудачных попыток, когда использовал hint, какие предметы не увидел, сколько раз застрял и причину. Критические стоп-сигналы: непонятно где кликнуть; puzzle всегда правильный с первого клика; ребёнок может пройти все 4 района нажимая Next; нет отличий between-before/after; движение рваное; фальшивый coin баланс; глобальный рейтинг поддельный.

**Критерий «можно играть»:** за первые 15 минут есть минимум 5 самостоятельных input decisions с consequences, 2 отличных по правилам mini games, 1 видимая мировая перемена, минимум 2 встречи NPC и 1 новая локация/проход. К 45-й минуте как минимум 3 вида puzzles и 2 отдельных района.

## 45. Финальное определение сдачи и запрет на «красивый обман»

**Задача считается выполненной как Game Expansion только если:** во вкладке `/play` можно самостоятельно пройти сюжет с реальными Puzzle Controllers и перемещением по четырём областям, два раза перезагрузить страницу без потери прогресса, увидеть новые рисунки мира после минимум 12 milestones, решить реально отличающиеся задания, открыть inventory/map/journal/achievements, получить один из двух финалов, продолжить side quests, а all required art проходит asset validation. **Target 90–120 minutes — только при подтверждённом прохождении людьми.**

**Задача считается выполненной как NEAR Hackathon Integration только если:** есть исходный и развёрнутый контракт, view методы, два реальных testnet аккаунта, GitHub Issue и PR, подписанный maintainer approval, confirmed withdrawal, explorer proof; failures / pending state корректны. Если что-то осталось недоделанным, это обозначено точно в `IMPLEMENTATION_STATUS.md` и на странице Live.

В финальном сообщении разработчик должен ссылаться на созданные ZIP/changed files и приложить краткий список реально пройденных тестов и сделанных скриншотов; слова «всё готово» без проверяемых артефактов недопустимы.

## 50. Пакет для нового чата: алгоритм работы AI-разработчика

1. Прочти эти требования и распакуй присланный веб-архив.
2. Сделай краткий baseline code audit с таблицей существующих файлов, реальными текущими функциями и критическими пробелами.
3. Начни код **сразу**: надёжный running build, engine split, actual SpriteAtlas, input, интерактивные puzzle boards, quest schema и autosave; не отправляй сначала «на выбор 3 концепта» или изображение вместо кода.
4. Создай art integration system и добавь/подключи все имеющиеся законные пиксельные ассеты; отсутствующие ассеты пометь через manifest и запроси/сгенерируй их только в рамках ожидаемого изображения. У пользователя будут свои графические референсы, поэтому не подменяй художественные требования произвольным стилем.
5. Сделай 1 законченный vertical slice Crossing с walking, 3 puzzle families, story NPCs, world transition и checkpoint; протестируй.
6. Расширь на 4 района и полный сюжет P1, затем добавь side quests, achievements, local leaderboard, world effects.
7. Integrate near-sdk contract and wallet/ GitHub Live flow as независимый модуль с проверкой. Не показывай testnet paid без RPC.
8. Проверяй все интерфейсы, видеозапись/скриншоты и точные команды; финальные файлы отдай в ZIP с README и status-report. Не включай в него старые raw exports без необходимости.
9. В финальном ответе не заявляй «прошёл 2 часа», если не проведён хотя бы один реальный timed playtest, и не заявляй «развернул контракт», если нет подтверждённого адреса и транзакций.

**Твоя задача — создать игру, в которой хочется задержаться, а не демонстрацию того, что маленький HTML умеет менять надпись.**
